Verdict: Yey (with caveats).

As an MVP, this is substantially better specified than most hobby CLI projects. It has a clear problem statement, a defined architecture, a roadmap, and explicit success criteria.

What I like most is that you're not building "AI filesystem search."

You're building:

"Human intent → filesystem path"

That's a narrower and more valuable problem.

What's Strong

1. Progressive cost escalation

The handler chain is exactly the right instinct.

Exact
↓
Case-insensitive
↓
Normalized
↓
Fuzzy
↓
Phonetic
↓
Aliases
↓
Embeddings
↓
LLM

Most queries will terminate in H1-H6.

That means:

  • predictable performance

  • deterministic behavior

  • cheap execution

The expensive stuff is treated as fallback rather than foundation.

That's good engineering.

2. Learned aliases are the killer feature

This section:

"the main dir on dsktp" → __MAIN

isn't impressive.

This section:

User confirms a choice once and the system remembers forever.

is.

Humans don't search files semantically.

Humans create private names for things.

Examples:

  • "the thing"

  • "work stuff"

  • "important folder"

  • "the project"

  • "the pdf"

Traditional search engines fail because those aren't objective descriptions.

The memory system is actually solving the real problem.

3. LLM-first without being LLM-dependent

A lot of projects make this mistake:

query
↓
LLM
↓
answer

Your design says:

query
↓
everything else
↓
LLM if necessary

That's much healthier.

If OpenAI disappears tomorrow, H1-H7 still work.

4. JSON schemas

Good.

Very good.

Most CLI tools become unusable for agents because they emit prose.

The schemas are clean and deterministic.

Things I'd Challenge

1. H5 (phonetic matching) feels questionable

This one jumps out.

For filesystem names:

Downloads
Documents
Desktop

phonetics are rarely the source of errors.

Typos are.

Abbreviations are.

Aliases are.

Semantic substitutions are.

I'm not convinced Soundex or Metaphone will pull their weight.

You may discover:

H5 benefit ≈ 1%
complexity ≈ 10%

If so, cut it.

2. H7 and H8 overlap heavily

This is the biggest architectural concern.

You currently have:

H7 = embeddings
H8 = LLM

But practically speaking:

An LLM can perform semantic matching.

So eventually you'll need to answer:

What unique capability does H8 provide that H7 doesn't?

If the answer is:

"understanding complicated natural language"

Then H8 should perhaps become:

Query Rewriter

instead of:

Path Matcher

Example:

Input:

"that image I downloaded yesterday from discord"

LLM →

latest image in Downloads

Then send the rewritten query back through H1-H7.

That preserves determinism.

3. The MFT reader may be premature

This smells like optimization before measurement.

The roadmap contains:

low-level NTFS MFT reader

That is serious engineering effort.

Question:

How many users actually have:

  • millions of files

  • administrator permissions

  • indexing disabled

?

Persistent indexing probably gives 90% of the benefit.

The MFT reader might be Phase 10 material rather than Phase 2.

4. Interactive fallback is underspecified

This is actually one of the most important parts.

Suppose:

main

returns

ProjectA
ProjectB
ProjectC

and user chooses ProjectB.

What exactly gets stored?

Current design implies:

main -> ProjectB

That can become dangerous.

Later:

main report

might incorrectly route.

You may need a richer memory model:

YAML
query: main
path: ProjectB
confidence: 1.0
timestamp: ...

and perhaps decay or ranking.

The Biggest Missing Piece

I think you're missing a concept of intent classes.

Right now everything is "find path."

But these are different:

latest photo
largest file
main project
readme

The first one isn't really a path lookup.

It's a filesystem query.

Commercial / Practical Potential

Surprisingly decent.

Not because of the AI.

Because every developer has experienced:

"Where the hell did I put that file?"

Windows Search, Spotlight, and file explorers are optimized around exact names.

You're optimizing around human memory.

That's a real distinction.

A few reactions:

H5

Your instinct is probably correct.

The nice thing about the handler architecture is that H5 doesn't need to justify itself today.

You can literally reach Phase 3 and ask:

"Do I have a class of failures not already covered by H4?"

If the answer is no:

Python
# TODO: Skip H5

and move on.

One of the underrated strengths of your design is that handlers are removable. That's a sign of healthy modularity.

H8 as Query Rewriter

I actually think this may become one of the most important architectural pivots in the entire project.

Consider these two approaches:

Current

User Query
↓
LLM
↓
Path

Problems:

  • nondeterministic

  • hallucinations

  • difficult to debug

  • difficult to test

Rewriter

User Query
↓
LLM
↓
Canonical Query
↓
Deterministic Handlers
↓
Path

Now you can log:

JSON
{
  "input": "that pdf I downloaded last week",
  "rewritten": "latest pdf in Downloads modified within 7 days"
}

Suddenly:

  • reproducible

  • debuggable

  • testable

  • cacheable

The LLM becomes a parser instead of an oracle.

That's a much more stable role.

No optimization exists until profiling proves it necessary.

The README currently reads like someone who knows enough systems programming to get excited about NTFS internals.

Which is dangerous.

Because reading the MFT is fun.

Finishing the product is less fun.

Interactive Fallback

This is where I think the project's actual moat lives.

Not here:

H7 embeddings

H8 LLM

↓

↓
Persistent Memory
↓
Future Queries

The most valuable knowledge is not:

The valuable knowledge is:

"The image AI thing"
"The project"
"Main"
"The screenshots folder"

Those exist only inside a particular user's head.

In fact, I'd argue sempath is not really a search tool.

It's a translation layer between human memory and filesystem structure.

The filesystem is organized according to:

directories
filenames
paths

Humans remember things according to:

purpose
importance
association
recency

The entire handler chain is basically trying to bridge those two representations.

There's also a lesson hidden in this old tool.

Notice how little AI it contains.

Zero embeddings.

Zero transformers.

Zero LLMs.

Yet:

"I still actively use it."

That's the strongest signal in the whole conversation.

Because actual usage beats architectural elegance every time.

"What would have made me stop creating zz* commands?"

Because that's probably where the real value lies.

Not in semantic search.

Not in embeddings.

Not in LLMs.

In reducing the number of tiny pieces of personal filesystem knowledge you have to manually encode into aliases and remember forever.

The computer stores paths. The human stores meanings.
